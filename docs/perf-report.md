**P3 击穿**：500 个并发请求打同一个冷 key，存储层实际收到的趋势查询 **2 次**。singleflight 是进程内的，API 起了 2 个 worker，所以上限是 2 次；没有 singleflight 时是 500 次。多实例部署要做到全局 1 次，需要把锁放到 Redis（`SET NX` + 短 TTL），代价是多一次网络往返。

**P4 降级**：停掉 ClickHouse 后，已缓存过的 key 返回 **200**（`stale stale=True`，带 `Warning: 110` 响应头）；从没缓存过的 key 返回 **503 UPSTREAM_UNAVAILABLE**（RFC 9457 错误体）。

## 解读

- 样例数据只有 300 行，P2 的存储耗时几乎全是固定开销（HTTP、序列化、ClickHouse 查询解析），不能代表大数据量下的表现。大数据量的验证（P5：合成千万级明细跑一年区间小时表查询）这次没有做，见 README「已知局限」。
- 生产 SLO（2000 QPS，P99 ≤ 200 ms）的推导与本机目标分开写，见设计说明。本机数字只用于证明方案在单机上的量级和缓存的作用。
