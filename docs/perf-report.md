## 结论与解读

> 本节手写，`perf/report.py` 重新生成时原样保留；上面的表格每次重新生成。P5 的 ClickHouse 服务端内存上限是 5.19 GiB（6 GiB 虚拟机的默认比例），4 个 vCPU 由 ClickHouse、API、k6 共用。

### P5：存储设计扛不扛得住

**目标对照**（存储层分段目标：日表一年 P99 ≤ 150 ms，小时表一年 ≤ 500 ms，明细 31 天 ≤ 1500 ms）：

| 段 | 串行 P99 | 8 并发 P99 | 结论 |
|---|---|---|---|
| 日表段 · 一年 | 2 ms | 11 ms | ✅ 远低于目标，读 6,588 行，和明细量无关 |
| 小时表段 · 一年 | 173 ms | **1,248 ms** | 串行 ✅，**8 并发 ❌**；16 并发一半查询内存超限（code 241） |
| 明细段 · 31 天 | 61 ms | 470 ms | ✅；16 并发 P99 982 ms 仍达标 |
| 端到端 · 小时表一年 | 2 / 5 RPS：247 / 160 ms | 10 RPS：P99 2.5 s，56% 失败 | 吞吐上限约 7.8 QPS，超过后排队撞上 2 秒超时（504） |

**结论：日表段和明细段扛得住；小时表段单查询够快，但不扛并发**，这是这次实测找到的真实短板。

1. **小时表几乎没有压缩行数**。1000 万事件摊到 5000 商品 × 3 平台 × 366 天 × 16 小时 ≈ 8,800 万个格子，每格平均 0.11 个事件，汇总后还有 945 万行（明细的 94.5%）。它省的是字节，不是行：去掉 event_key 后压缩后 63 MB，是明细 427 MB 的 1/7。按设计说明的生产假设（日增 1000 万、30 万 SKU × 10 平台 × 24 小时 = 7,200 万格/天），格子同样稀疏，**「商品 × 小时」这一层在生产上也接近明细行数**。
2. **一年区间的小时表查询是全表扫描**。排序键以 product_id 打头，但每个月分区约 79 万行、每个商品约 158 行，一个 granule（8192 行）横跨约 50 个商品；maxi dress 占 10% 且分散，每个 granule 里都有命中商品，稀疏索引一个也跳不过去。read_rows 1,064 万 ≈ 全表。单查询 4 个线程吃满 4 个 vCPU，所以 2 并发起延迟就线性上涨、QPS 封顶在 7.8。
3. **FINAL 是主要成本**（见下节）：去掉 FINAL 后同一查询 8 并发 P99 298 ms，达标。
4. 首轮测量（刚灌完数据、重算完）比稳定后慢 3–4 倍（小时表串行 P99 753 ms、明细 334 ms），同一库连跑三轮后稳定在表中数字。表中是稳定值；生产上刚完成大批量回填后的几分钟会更慢。
5. **重算**：全年小时表 945 万行先删后写 7.0 s；品类日表每个预设时区全年 0.3–1.6 s。生产节奏是每 5 分钟重算最近 3 小时，量级是这里的 1/3000，不是瓶颈。
6. **压缩比**：明细只有 1.36，因为 event_key 是 32 位随机十六进制串（每行 32 字节、几乎不可压），占明细体积的大头；生产改用采集方的 `source + source_event_id` 后会明显好转。汇总表 4.35，日表 6.67。

**建议（按收益排序，本次未改主代码）**：

- 小时表查询去掉 FINAL，改由重算保证无重复（见 O7 建议），8 并发 P99 从 1,248 ms 降到 298 ms，吞吐 ×4，单查询内存从 220 MB 降到 1 MB。
- 为「当前默认规则版本」再物化一张**品类 × 平台 × UTC 小时**表（maxi dress 一年 3 × 8,784 = 2.6 万行）。设计说明当初拒绝「按品类汇总」是因为改规则要重算；折中是商品小时表仍是事实来源，品类小时表只为默认版本建、改规则时随日表一起重算。这样任意整点时区也能像日表一样毫秒级返回。
- 运维上限制并发重查询：ClickHouse 侧给 API 用户设 `max_concurrent_queries_for_user` 或 `max_memory_usage`，让过载表现为快速 429/503，而不是全体 OOM。

### O7：FINAL 是不是双保险，成本多大

三段查询去掉 FINAL 后结果**完全一致**（日表与小时表全年合计都是 9,490,029，明细 31 天 797,621），说明稳定状态下表里没有重复行，FINAL 是兜底。成本：

| 段 | 串行 P50（有 / 无） | 8 并发 P99（有 / 无） | read_bytes（有 / 无） | 峰值内存（有 / 无） |
|---|---|---|---|---|
| 日表 | 1 / 1 ms | 11 / 10 ms | 相同 | 相同 |
| 小时表 | 128 / 30 ms | 1,248 / 298 ms | 266 / 161 MB | 220 / 1.1 MB |
| 明细 | 50 / 11 ms | 470 / 113 ms | 185 / 43 MB | 120 / 0.3 MB |

- FINAL 要读完整排序键加版本列再做归并：明细段多读了 32 字节的 event_key 和 ingested_at，read_bytes 是 4.3 倍；归并要缓存数据，内存放大两个数量级，**高并发下的 OOM 就是它造成的**。
- 试过 `do_not_merge_across_partitions_select_final = 1`（按月分区、同一个键不会跨分区，所以安全）：小时表串行 P99 173 → 131 ms，8 并发 1,248 → 1,148 ms，改善有限，不改变结论。
- **重复从哪来**：明细的去重在写入前完成（批内 + 跨批查已有 key），但「查已有 key → 写入」不是原子的，两个批次并发导入同一份数据时会写进重复行；汇总表是「先删后写」两条语句，两个重算任务重叠时也会留下重复行。FINAL 防的就是这两种情况。

**建议**：

| 位置 | 建议 | 理由 |
|---|---|---|
| 重算 SQL 里读 fact_sales 的 FINAL | **保留** | 每 5 分钟付一次，换来汇总一定建立在去重后的明细上 |
| 日表段 | 保留 | 6,588 行，成本为零 |
| 小时表段 | **去掉**，前提是重算改成原子替换 | 重算写临时表后 `ALTER TABLE … REPLACE PARTITION` 整分区原子替换，再加调度锁保证单写者；这样不会出现重复，也没有「删了还没写」的空窗（FINAL 防不了这个空窗） |
| 明细段 | 保留 | 区间上限 31 天，带 FINAL 8 并发 P99 470 ms 已在目标内；并发导入的竞态只能靠它兜底 |

### P6：「按整个响应做缓存」的命中率取决于用户怎么选区间

- **任意区间命中率 11.2%，20 个热点 key 99.8%**，同样 200 RPS × 120 秒、同样从空缓存开始。`/metrics` 与 k6 按 `X-Cache` 计数完全一致（2,677 / 24,000 与 23,960 / 24,001），多 worker 汇总口径得到验证。
- 原因是 key 空间：73 天内长度 1–73 的区间约 2,700 种 × 7 种平台组合 × 6 个时区 × 3 种粒度 ≈ 34 万个 key，两分钟 2.4 万个请求绝大多数是第一次出现。回源率 0.918：每个请求平均打 0.92 段 SQL（混合计划一次算 2 段，抵消了一部分命中）。
- 这一场如果在生产上出现，命中率会远低于 85% 的预警线、也低于 SLO 的 90%。告警是对的：它说明流量形态变了，缓存已经不是主要防线。
- 好在未命中的成本取决于走哪一段：P6 里 20,606 个只走日表段的请求服务端平均 2.8 ms，P5 证明日表段在千万级下仍是毫秒级。**真正的风险是「任意区间 + 非预设整点时区」**，它落到小时表段，吞吐只有个位数 QPS。
- 改进方向：① 缓存粒度从「整个响应」下沉到「（品类, 规则版本, 时区, 平台, 本地日）」的日格子，响应由日格子拼出来，任意区间之间可以共享；② 前端把自定义区间收敛到预设区间（近 7 / 30 / 90 天、整月）；③ 上面提到的品类小时表。
