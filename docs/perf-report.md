**P3 击穿**：500 个并发请求打同一个冷 key，存储层实际收到的趋势查询 **2 次**。singleflight 是进程内的，API 起了 2 个 worker，所以上限是 2 次；没有 singleflight 时是 500 次。多实例部署要做到全局 1 次，需要把锁放到 Redis（`SET NX` + 短 TTL），代价是多一次网络往返。

**P4 降级**：停掉 ClickHouse 后，已缓存过的 key 返回 **200**（`stale stale=True`，响应头 `x-data-stale: true`）；从没缓存过的 key 返回 **503 UPSTREAM_UNAVAILABLE**（RFC 9457 错误体）。

### 小时表段对照实验：v1.2.0 的 1.2 秒根因是全表扫描，不是 FINAL

v1.2.0 的结论写的是「FINAL 是主要成本」。**这个结论不准确**。正式 SQL 轮把商品层（v1.2.0 的 B 段读的就是它）放在两组状态下测，结论如下（一年 Europe/Berlin，三种做法一年总销量都是 9,490,029）：

| 商品层查询（带 FINAL） | parts | 串行 P99 | 8 并发 P99 | 16 并发 | 峰值内存 | read_rows |
|---|---|---|---|---|---|---|
| 重算后（与 v1.2.0 同一状态） | 60（每月 4–5 个） | 154 ms | 1,453 ms | P99 2.6 s，160 个里 44 个内存超限（code 241） | 222 MB | 1,131 万 |
| OPTIMIZE 后 | 12（每月 1 个） | 33 ms | 221 ms | P99 461 ms，0 失败 | 0.8 MB | 986 万 |
| OPTIMIZE 后，去掉 FINAL | 12 | 36 ms | 237 ms | P99 491 ms | 1.0 MB | 986 万 |
| **品类 15 分钟表**（替代方案，OPTIMIZE 后） | 12 | **2 ms** | **13 ms** | **P99 23 ms，256 QPS** | 0.3 MB | **7 万** |

1. **根因是全表扫描**。数据很稀疏，商品层的行数约等于明细（15 分钟粒度 986 万 / 1000 万，小时粒度 945 万）；品类内的商品又分散，以 `product_id` 打头的排序键一个 granule 也跳不过，一年区间每次读近千万行。合并完、不加 FINAL 也要 237 ms（8 并发），4 核上吞吐封顶约 40 QPS。
2. **FINAL 的代价随 part 数增长，part 合并后可以忽略**。每个月 4–5 个 part 时，FINAL 要在查询时跨 part 归并，内存 222 MB、耗时放大约 6 倍，16 并发就撞内存上限；每个分区只剩 1 个 part 时不需要跨 part 归并，加不加 FINAL 几乎一样（221 vs 237 ms）。明细段同理：31 天 8 并发 P99 475 → 95 ms。
3. v1.2.0 的 1.2 秒 = 全表扫描 × 分片未合并让 FINAL 放大 × 4 核上 8 个查询排队。

**对策（已实现）**：B 段改读品类表，商品层退为重算中间层、不在查询路径上，它上面的 FINAL 问题也就不存在了。品类表每个分区本来就只有 1 个 part（一次重算每个分区只写一次），合并前后差别不大（重算后 8 并发 P99 24 ms，OPTIMIZE 后 13 ms）。

### 粒度：小时还是 15 分钟（先实测，再拍板）

同一份 P5 数据、同一轮手工 clickhouse-benchmark（10-22 晚，品类层已 OPTIMIZE），一年区间：

| 品类层 | 行数 | 串行 P99 | 8 并发 P99 / QPS | 16 并发 P99 / QPS |
|---|---|---|---|---|
| 小时（Europe/Berlin） | 17,568 | 3 ms | 14 ms / 888 | 21 ms / 1,123 |
| 15 分钟（Europe/Berlin） | 70,272 | 3 ms | 15 ms / 800 | 27 ms / 932 |
| 15 分钟（Asia/Kathmandu，+05:45） | 70,272 | 3 ms | 19 ms / 833 | 30 ms / 925 |

（这里的 QPS 是 clickhouse-benchmark 自报的，比 `perf/p5.py` 里按墙钟、含 docker exec 启动开销算的 QPS 高。）

行数 ×4，16 并发吞吐少约 17%，仍远低于目标。换来的是：+05:45 这类非整点时区的已封口日也读品类表；未封口那天能在封口线处切开。所以**把小时表换成 15 分钟表**（商品层同步改成 15 分钟，否则品类层没有上游），没有两张表并存：两张表并存要多一套重算、多一种对拍，收益只是 B 段少 17% 的吞吐差。

### 实时路径：当天按封口线切开，以及明细排序键

**切开本身**：规划器在未封口那天里按 `sealed_until` 切开，前半天读品类 15 分钟表，只有 `[sealed_until, 日终)` 读明细；封口线按 15 分钟对齐。

**但在 product_id 打头的明细上，切开一行都没省**（正式 SQL 轮，OPTIMIZE 后）：

| 明细查询（v1 品类，带 FINAL） | read_rows | 串行 P99 | 8 并发 P99 | 16 并发 P99 |
|---|---|---|---|---|
| 12-31 一整天（优化前的实时明细段） | 851,115 | 6 ms | 51 ms | 90 ms |
| 12-31 12:00 之后的半天尾巴 | 851,115 | 10 ms | 47 ms | 105 ms |

两者都读了整个 12 月分区：品类商品分散，时间条件在 product_id 打头的排序键上跳不过 granule。所以又把明细排序键改成 `(event_ts, product_id, event_key)`——明细在查询路径上只剩「全部商品 × 一小段时间」，重算也按时间区间扫，两者都适合时间打头。同一份 1000 万行数据（10-23 对照，均已合并成每月 1 个 part）：

| 明细排序键 | 查询 | read_rows | 串行 P99 | 8 并发 P99 / QPS | 16 并发 P99 / QPS |
|---|---|---|---|---|---|
| product_id 打头 | 一整天 | 851,115 | 10 ms | 61 ms / 236 | 141 ms / 231 |
| product_id 打头 | 半天尾巴 | 851,115 | 7 ms | 56 ms / 233 | 113 ms / 263 |
| **event_ts 打头** | 一整天 | 40,107 | 3 ms | 28 ms / 701 | 25 ms / 1,028 |
| **event_ts 打头** | 半天尾巴 | **31,915** | **4 ms** | **15 ms / 841** | **24 ms / 1,044** |

- 优化前（product_id 打头、整天读明细）→ 优化后（event_ts 打头、只读尾巴）：明细段 8 并发 P99 61 → 15 ms，16 并发 141 → 24 ms，吞吐 ×4.5。主要收益来自排序键；切开的收益在生产上才明显——生产的尾巴至多「15 分钟 + 一个重算间隔」，而不是这里模拟的半天。
- 代价：明细压缩后体积 +2.6%（436.9 vs 425.7 MB）；「一组商品 × 很长时间」的明细查询不再能按商品跳读，但这类查询已不在查询路径上（只剩 1972 年前地方平时那种零头）。
- 这组对照是用 clickhouse-benchmark 直接测的（QPS 是工具自报值），不是 `make perf-p5` 的产物；`make perf-p5` 下一次运行会按新 DDL 建表，上面「各段查询」表里的 fact_* 行届时会反映新排序键。

**C 段 31 天上限与单独限流**：核实 v1.2.0 时两条都没落实；本轮先补上，改成 15 分钟粒度后又撤掉了——明细只剩尾巴，任何请求都造不出长区间的明细扫描，留着只会把能毫秒级返回的 Kathmandu 一年请求拒成 400。剩下的风险是重算停摆让尾巴变长，应监控 `now − sealed_until`，见 design.md §5。

- **波动**：同一路径在相邻档位上不单调（日表段 200 RPS 83 ms、300 RPS 14 ms；Kathmandu 已聚合 200 RPS 115 ms 而 Berlin 同样的表在 300 RPS 才 27 ms）。每档只跑一轮 60 s，这台 4 vCPU 虚拟机上 200 RPS 以上的单轮 P99 要看成区间，拐点误差约一档。Kathmandu 已聚合与 Berlin 读同一张表、同样行数，没有结构性原因更慢，判断是单轮波动，但照实记为 100 RPS。
- **低到达率反而慢**（10 RPS 时 P99 27–37 ms，50 RPS 起降到 10–25 ms）：请求稀疏时 worker 与 ClickHouse 线程反复从空闲唤醒、连接冷了，每个请求都付这笔固定开销。不影响结论。
- **瓶颈在哪一侧**：拐点下一档时虚拟机里 API + ClickHouse 合计约 260–330%（上限 400%），k6 在宿主机上只用 10–20%，不是瓶颈。已聚合路径 API 与 ClickHouse 大致各半；实时路径 ClickHouse 约是 API 的 2 倍（每个请求两到三段 SQL，其中一段是明细）。API 两个 worker 合计 130–150% 时延迟已经明显上升：单个 Python 进程在 GIL 下约能用满 0.7–0.8 核。

### 实时路径优化前后（同样的到达率）

优化前 = 品类小时表 + 未封口的一整天读明细（product_id 打头）+ Kathmandu 整段读明细（10-22 基线）；优化后 = 15 分钟品类表 + 只有封口线之后读明细 + event_ts 打头的明细（10-23 正式端到端轮）。完整的 P50 / P95 / P99 与失败率见上面「实时路径优化前后」表。

| 场景 | 200 RPS P99（前 → 后） | 300 RPS P99（前 → 后） | 400 RPS P99（前 → 后） | 拐点（前 → 后） |
|---|---|---|---|---|
| UTC | 57 → 21 ms | 257 → **106 ms** | 394 → 174 ms | 200 → **300 RPS** |
| Europe/Berlin | 56 → 68 ms | 653 → **56 ms** | 997 → 190 ms | 200 → **300 RPS** |
| Asia/Kathmandu | 59 → 78 ms | 252 ms + **15.8% 失败** → 157 ms、0 失败 | 未测 → 373 ms | 200 → 200 RPS（300 RPS 从「16% 超时」变成「略超目标」） |

- 200 RPS 以下前后都达标，差异在单轮波动范围内；收益集中在 300 RPS：UTC 与 Berlin 从不达标变成达标，Kathmandu 不再超时。
- SQL 层（clickhouse-benchmark，见上一节）：明细段 8 并发 P99 61 → 15 ms、16 并发 141 → 24 ms、吞吐 ×4.5。端到端的收益比 SQL 层小，因为到了 300–400 RPS，虚拟机里 API 和另外两段汇总查询也在抢同样的 4 个核。
- 实时 Kathmandu 优化后 300 RPS 仍略超 150 ms（157 ms）。原因没有单独拆解：它与 UTC、Berlin 读同样的表，只是 ClickHouse 侧 CPU 更高（300 RPS 时 185%，UTC 176%、Berlin 122%），也可能是单轮波动。没有再做针对性优化。

### 容量：缓存命中路径与 API worker 数

`make capacity`（样例库，20 个热点 key 全部命中，每档 30 s）。第一次尝试按原计划加到 2,000 RPS 时，k6 出现 0.8% 失败，随后 colima 的宿主机端口转发与 docker socket 一起失去响应（虚拟机里的容器都还在正常运行），只能 `colima restart`。所以命中路径的有效上限只测到 1,500 RPS：**这是压测环境的上限，不是服务的拐点**。

| worker | 250 / 500 / 750 / 1,000 / 1,250 / 1,500 RPS 的 P99 ms | 1,500 RPS 时 API CPU | 结论 |
|---|---|---|---|
| 2 | 3.0 / 3.3 / 2.7 / 3.2 / 24.1 / 7.5 | 104% | 1,500 RPS 达标；1,250 那一档的 24 ms 是单轮尖刺（下一档 7.5 ms） |
| 4 | 3.6 / 4.0 / 18.8 / 6.5 / 7.4 / 11.9 | 101% | 1,500 RPS 达标；750 那一档 18.8 ms 同样是尖刺 |

- 1,500 RPS 时 API 只用了约 1 个核（虚拟机 4 核），命中路径每个请求约 **0.7 ms·核**。按 60% 利用率外推，单台 4 vCPU 约能扛 2.4 ÷ 0.7 ms ≈ **3,400 RPS** 命中请求（推算，未实测）。
- **2 个 vs 4 个 worker**：所测范围内没有可见差别（同样的 CPU、同样达标，尖刺各有一次），**默认值保持 2**，改成了环境变量 `API_WORKERS`。4 个 worker 的收益要在 API 吃满 2 个核以后才可能出现，这台机器的端口转发在那之前就先垮了，没能验证。
- 与 v1.2.0 的 P1（1,000 RPS，P99 1.5 ms）同一量级。

万级推算见 [design.md §7.4](design.md)（公式、假设、实测输入都在那里）。

### P5 其他观察

1. **商品层几乎没有压缩行数**。1000 万事件摊到 5000 商品 × 3 平台 × 366 天 × 64 个 15 分钟格，每格平均不到 0.03 个事件。它省的是字节（压缩后 60 MB，是明细的 1/7），不是行。按设计说明的生产假设（30 万 SKU × 10 平台），格子同样稀疏，**商品层在生产上也接近明细行数**——这正是它不能留在查询路径上的原因。
2. **重算**：商品 15 分钟层全年 986 万行先删后写 2.0 s；品类 15 分钟表 0.2 s；品类日表每个预设时区全年 0.2–0.6 s。生产节奏是每 5 分钟重算最近 3 小时，量级是这里的 1/3000，不是瓶颈。
3. **压缩比**：明细只有 1.36，因为 event_key 是 32 位随机十六进制串，几乎不可压；生产改用采集方的 `source + source_event_id` 后会明显好转。
4. **运维建议**：ClickHouse 侧给 API 用户设 `max_concurrent_queries_for_user` 与 `max_memory_usage`，让过载表现为快速 503；大批量回填后先等合并（或主动 `OPTIMIZE … FINAL`）再放流量；监控 `now − sealed_until`，重算停摆时明细尾巴会变长。

### P6：「按整个响应做缓存」的命中率取决于用户怎么选区间

- **任意区间命中率 11.2%，20 个热点 key 99.8%**，同样 200 RPS × 120 秒、同样从空缓存开始。`/metrics` 与 k6 按 `X-Cache` 计数完全一致（2,677 / 24,000 与 23,960 / 24,001），多 worker 汇总口径得到验证。
- 原因是 key 空间：73 天内长度 1–73 的区间约 2,700 种 × 7 种平台组合 × 6 个时区 × 3 种粒度 ≈ 34 万个 key，两分钟 2.4 万个请求绝大多数是第一次出现。回源率 0.918：每个请求平均打 0.92 段 SQL（混合计划一次算 2 段，抵消了一部分命中）。
- 这一场如果在生产上出现，命中率会远低于 85% 的预警线、也低于 SLO 的 90%。告警是对的：它说明流量形态变了，缓存已经不是主要防线。
- 好在未命中的成本取决于走哪一段：P6 里 20,606 个只走日表段的请求服务端平均 2.8 ms，P5 证明日表段在千万级下仍是毫秒级。v1.2.0 时的风险是「任意区间 + 非预设整点时区」落到商品小时表段、吞吐只有个位数 QPS；B 段改读品类 15 分钟表后，这条路径与日表段同一量级（见 P5）。
- 改进方向：① 缓存粒度从「整个响应」下沉到「（品类, 规则版本, 时区, 平台, 本地日）」的日格子，响应由日格子拼出来，任意区间之间可以共享；② 前端把自定义区间收敛到预设区间（近 7 / 30 / 90 天、整月）。（v1.2.0 时列的第三条「品类小时表」已实现，并进一步做成了 15 分钟粒度。）
